## 2. 中断原因及责任边界

应用日志的关键记录：

1. 22:55:27：正式 CE seed42 的 epoch-002 已持久化并由独立进程加载。
2. 22:56:13：该模型 frozen 包完成同样的持久化与加载校验。
3. 22:56:20：正式 mixed seed42 开始训练。
4. 23:22:12：mixed seed42 的 epoch-001 已持久化并独立加载。
5. 23:42:09：Modal 明确记录 preemption，并声明将使用同一输入重启函数。
6. 23:42:14：重启后的编排在 `modal_laya_deferred.py:97` 抛出 `Workflow already started; refuse automatic duplicate/retraining`，随后 runner 终止。

直接触发因素是平台抢占；任务没有继续完成，是本地实现的编排恢复缺陷：一次性 `coordinator-started.json` 标记能阻止重复整批训练，却没有区分用户重复提交与平台对同一任务的合法重启。异常处理还会取消正在等待的 GPU 子调用。现有逐 epoch 检查点保住了训练状态，但编排没有利用这些状态恢复工作队列。

因此，`retries=0` 不能当作「平台绝不会重新执行」的保证。Modal 的 [抢占说明](https://modal.com/docs/guide/preemption) 明确要求长任务可安全重入，并说明抢占后会以同一输入重启。这个故障不是已经证明的损失函数失效，也不是当前日志显示的 FP32 数值溢出。

完整日志保存在原实验目录的 `app-terminal.log`；云端状态、准入和文件清单保存在同目录的 `cloud-*.json` 与 `cloud-snapshot/`。这些原始快照不改写为成功状态。

## 4. 目前能分析的训练诊断

正式 CE seed42 已记录 5,526 次连续更新、44,200 次样本暴露；两个 epoch 的训练 CE 为 0.20100774 和 0.06210908。训练与独立重载的云端墙钟合计约 51.2 分钟，峰值已分配显存约 7.83 GiB，峰值保留显存约 8.43 GiB。

mixed seed42 已接收的 5,086 条更新日志连续，记录的目标损失、共同 CE 和裁剪前梯度范数均为有限数。第一 epoch 的混合目标均值为 0.14337008，但按相同未平滑 CE 口径计算是 0.20475191；同期 CE 分支为 0.20100774。这些均值按训练循环逐 batch 平均，末尾小 batch 没有另做样本加权。

**不能把 0.1434 对比 0.2010 解释为改进。** 两个分支优化的目标不同；即使使用共同 CE，训练内损失也不等于开发集准确率，且当前只有一个种子、没有完整固定预算模型配对。这里仅核查执行与数值状况，不作方法筛选。

本次重新校验了冻结协议绑定的 122 项文件，SHA 全部一致；训练源码、数据划分和实验配置未在接收过程中修改。官方测试没有用于本轮调参或补评。
